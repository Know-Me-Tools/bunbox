# Local unanswered-demo profile

The `bunbox-mcp` executable accepts one pinned read-only recipe over stdio MCP on macOS ARM64. Each accepted job receives a separate Microsandbox VM. UAR owns account and folder admission and passes only minimized header projections. The BunBox launcher derives the owner and run from the trusted caller before it starts the server.

## Configure

Build the `bunbox-mcp` package and use a separately provisioned Microsandbox 0.7.2 Darwin ARM64 installation. Keep its verified `msb` and `libkrunfw.5.dylib` together. Set `BUNBOX_MSB` to that executable and `MSB_HOME` to its private local state containing the pinned ARM64 `oven/bun:1.4.2` image. Use a short MSB_HOME path that accommodates the per-VM Unix socket. The launcher supplies a private absolute `BUNBOX_STATE_DIR`, `BUNBOX_OWNER` and `BUNBOX_RUN`. Issue a fresh stdio session per owner/run. The state directory is shared by this installation and must be inaccessible to other OS users. A single OS owner controls the server and executable.

The CLI creates the VM with one CPU, 256 MiB memory, network disabled, zero shared mounts and no image pull. The worker sends the pinned recipe and its bounded input over a dedicated relay using the 0.7.2 agent client. Program execution has a 30-second deadline and guest limits on CPU time, processes, open files and file writes. The relay has a 64 KiB frame bound, a 256 KiB queue-byte budget, and a separate cumulative output bound of 64 KiB. The upstream initial handshake still uses its own larger bounded codec. Only the pinned guest image and recipe are admitted.

## Tools

- `submit` takes a bounded `requestKey`, the SHA-256 of [the exact recipe](../runtime/recipes/unanswered-demo-v1.ts), and `input` containing an integer inclusive cutoff, inbox/sent coverage booleans and up to 2,000 header rows. The serialized input limit is 2 MiB. Each row supplies a source reference, optional thread reference, timestamp, direction and optional subject. A successful submission returns a job ID.
- `get` takes the job ID from the receipt. Poll it until terminal. A successful result returns up to twenty source-linked unanswered findings, bounded unassigned references, coverage, truncation and input/result/recipe digests. Missing inbox or sent coverage yields zero confirmed unanswered findings. The fixed English-language subject heuristic can miss other phrasings. Thread association and source resolution remain connector responsibilities.
- `cancel` takes the same job ID. It requests cancellation; the final receipt reports cancellation only after teardown. An admission retry with the same key and identical input returns the existing receipt. A changed input returns a conflict. A different owner or run cannot poll, cancel or replay the existing job.

The detached worker holds an installation-wide execution lease. Disconnecting from stdio leaves an accepted job running. After a worker interruption, get reconciles the named VM and marks the outcome unknown. The creation process inherits the execution lease. A durable creation-intent marker prevents reconciliation from treating an empty registry as proof that an interrupted boot will stay absent. When creation or teardown cannot be confirmed, the receipt reports `cleanup_unknown` and the installation retains its reservation. Poll the original job after recovering the runtime. If no instance ever became observable, the operator must reconcile the dedicated installation before admitting more work. The job ledger never repeats an uncertain execution and never exposes guest stderr or an unvalidated output channel. Operators can disable the profile by removing the host's staged admission while keeping the same local state accessible for outstanding job reconciliation.
